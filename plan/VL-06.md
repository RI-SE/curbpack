# VL-06 — Review affected Claims after a Requirement change

## Decisions recorded for this plan

- The headless function is `claims_affected_by_requirement(claims, before, after)`. A Claim is affected when its `namespace`, `pack_id`, `requirement_id`, and `requirement_digest` equal the Requirement before the save, and `version_digest(after)` differs from `version_digest(before)`. An equal digest returns an empty list. The function returns the Claim id and the recorded binding beside the current Requirement identity and digest. It writes nothing.
- Reopening uses `claims_unresolved_for_requirement(claims, requirement)`. A Claim is unresolved when the same namespace, pack id, and requirement id are recorded and `requirement_digest` differs from `version_digest(requirement)`. There is no queue file. Claims that still match the current digest are not unresolved.
- Both functions read Claim objects the caller already loaded. The caller loads the open product repository's `claims_dir` with `validate_claim(read_json(path))`. It does not call `load_claim` or `load_claims`, because those may write.
- The Requirement that was saved is the selected working copy. The Claims that are inspected are the Claims in the currently open product repository. A Claim is affected only when its stored binding equals that Requirement's identity and previous digest. Claims in another repository are not read.
- Compare Apply uses the same two functions for the destination Requirement. It does not grow a second comparison.
- Take Ownership uses `claims_after_ownership(claims, owned)`. On the Requirement editor GET after the redirect, the source list matches `origin.namespace`, `origin.pack`, and `origin.requirement` to the Claim's `namespace`, `pack_id`, and `requirement_id`. Claims bound to the owned Requirement's namespace, pack id, and id stay in the owned list. The source list is not given binding status `stale`. No Claim is rewritten and no queue file is written. The page may link each source Claim to explicit rebind onto the owned Requirement.
- The Requirement editor page renders the lists and three links. Review Claim is a GET of the existing `/claims` editor. The query carries the proposed Requirement's namespace, pack id, and requirement id. The fragment is `#claim-{id}`. The model does not filter on a `claim` query. That GET already renders `claims_page`. It does not use POST `/claims/{id}`, which saves the Claim. Discovery opens the existing `/discover/claims/{requirement_id}` workflow for the open repository and pack. Later is a link that posts nothing. The rendered Requirement page and `studio/pack/pages/compare_form.ts` do not decide which Claim is affected. `studio/pack/requirement_editor.py` may keep its existing `version_digest` check for the save's expected digest. Reopen calls `claims_unresolved_for_requirement`.
- Explicit rebind stays `rebind_requirement` in `claims/bind.py`. The rebind POST carries namespace, pack id, and requirement id. The Requirement is matched by all three. A test uses two Requirements that share an id and differ in namespace and pack id. A changed binding drops `signed`. `source`, `args`, `checks`, and `description` stay unless the user edits them in the existing editor.
- An unchanged save still saves the Requirement through the existing path. The affected list is empty. Claim files, Run Result files, and Review Report files are not opened for writing by this story.
