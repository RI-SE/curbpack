# VL-04 — Bind Claims to exact Requirements

## Summary

- **Story:** `docs/agile/epics/11-pack-version-lifecycle/stories/VL-04-Bind-claims-to-req.md`
- **Goal:** A Claim records the Requirement namespace, pack id, requirement id, and payload digest it was assessed against. Curbcheck reports `match`, `stale`, or `missing` and still runs the configured Checks. Review shows that binding apart from the Claim signature and the Check outcomes.
- **Scope / exclusions:** No new Check type. No change to Check execution. Discovery and the Claims editor call one backend operation to record a binding. Curbcheck uses the same resolution and `version_digest` rules when it writes the Run Result. Review renders that stored row. The UI does not calculate digests or decide binding status. Ordinary edits do not change the binding. An ordinary edit that changes the signed payload still drops `signed`. An explicit rebind is a separate function from Save.
- **Baseline:** `make test` outside the sandbox at `725361c1eb3070572c55d5fb18d8d28458b062a1`: 500 PASS, 0 FAIL. VL-03 is closed at `5face1c`.

## Decisions recorded for this plan

- The Requirement digest is `version_digest` of the Requirement object, the same digest Packs v2 already uses. No second digest function.
- Resolution uses the repository's one pack version directory from `checks/run.py` `_pack_version_dir`. That function already rejects a pack id with more than one version directory.
- `namespace` on the Claim is the Requirement's namespace. `pack_id` is the Pack id. `requirement_id` stays the existing field. `requirement_digest` is the digest recorded at bind time.
- A resolved Requirement whose digest equals `requirement_digest` is `match`. The same id with a different digest is `stale`. An identity that does not resolve, including a namespace that is not the loaded Pack's namespace, is `missing`. `actual_digest` is present for `match` and `stale`, and absent for `missing`.
- Binding status does not skip, fail, or change a Check. The Check status aggregate stays `pass`, `fail`, or `skipped`.
- Maintainer, 2026-11-16: VL-04 wins over the old Run Result sentence. `docs/reference/outputs.md` is updated. A new Claim row keeps `id`, `digest` (the Claim digest), `status` (the Check aggregate), and `checks`. It also carries `namespace`, `pack_id`, `requirement_id`, `requirement_digest`, `binding` (`match`, `stale`, or `missing`), and `actual_digest` when the Requirement resolves. Those fields sit on the Claim row only. A Check row does not repeat them. A historical row with only `id`, `digest`, `status`, and `checks` still validates. Reading it does not write the file.
- `missing` is shown from that stored Claim row. `review/compile.py` keeps its existing rejection when a report's Requirement object is absent. That rejection is outside this Run Result decision.
- Save stays `rebind` / `rebind_from_fields`. It never writes a new Requirement identity or digest. `rebind_requirement` is the only function that does. Discovery and the Claims editor both call it for an explicit rebind. The page sends the selected Requirement. The function resolves it and records `version_digest`.
- A Claim fixture that gains the binding fields and whose test expects a valid seal is re-signed in the same step. The new fields are part of the signed payload.

## Run Result row

`digest` remains the Claim digest. `status` remains the Check aggregate. `binding` is the separate Requirement status. `actual_digest` is omitted when `binding` is `missing`. No other Run Result field is added.
